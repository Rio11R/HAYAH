# HAYAH — القرارات التقنية المعلقة

**الحالة: PROPOSED — توصيات للمراجعة، لا قرارات نهائية.** المرجع MPS v0.3، خصوصًا الأقسام 3 و5 و7–9 و14. البيانات `0.3-draft` ووجود `schema_basis` لا يعتمدان DEC-06. أدوات Python للقراءة في Phase 1 لا تعتمد Python كتقنية التطبيق.

وفق توضيح الريان، أحمد مرشد ومعتمد قرارات وليس عضوًا في فريق التنفيذ الخماسي: الريان، نور، عبدالإله، عمار، تاج. يُحفظ MPS الأصلي دون تعديل؛ سطر الأسماء في مقدمته يحتاج تصحيحًا موثقًا لاحقًا.

## DEC-04 — آلية محرك السيناريوهات

**الحالة الحالية:** وظيفة السيناريوهات الثلاثة والمقارنة والتوصية والقرار البشري معتمدة نطاقًا في DEC-09؛ نوع المحرك والقواعد غير معتمدين.

**الخيارات:**

1. محاكاة أحداث منفصلة مبسطة DES: أحداث وصول/بدء خدمة/انتهاء خدمة وقوائم انتظار وموارد؛ أقرب لوصف العرض، لكنها تحتاج أوقات خدمة، أفقًا زمنيًا، وقواعد جدولة واختبارات أكثر.
2. قواعد حسابية حتمية للسيناريوهات: تغيرات تشغيلية محدودة معلنة ومقارنة قابلة للتكرار؛ أسرع في التطوير والشرح، لكنها لا تمثل DES ولا تكفي وحدها لادعاء أوقات انتظار واقعية.

**التوصية المقترحة:** قواعد حتمية صغيرة للنموذج الأولي إذا وافق أحمد على ملاءمتها للعرض والوقت المتاح. توثيق كل قاعدة ومدخلاتها وافتراضاتها ومثال يدوي قبل الكود. إذا كان تنفيذ DES نفسه شرطًا للعرض، فاعتماد DES مبسطة بدل استخدام التسمية لقواعد حسابية. لا اختيار تلقائي عند غياب الرد.

**الأثر:** يتوقف تنفيذ المحاكاة ونتائج الانتظار والمقارنة العددية والتوصية على هذا القرار. إذا اختيرت القواعد دون DES، يجب تصحيح وصف DES في العرض التقني أو وصفه هدفًا مستقبليًا وفق MPS §8. يجب أن تبدأ البدائل الثلاثة من نسخة واحدة ثابتة وأن يبقى أصل البيانات دون تعديل.

**المسؤولون عن الحسم:** الريان + أحمد كما في سجل MPS؛ عبدالإله يراجع رحلة المريض، ونور تراجع قابلية عرض النتائج، وعمار وتاج يراجعان افتراضات الموارد. اعتماد أحمد لازم لتغيير وصف المحاكاة أو عقدها.

## DEC-05 — تقنية التطبيق

**الحالة الحالية:** HTML/CSS/JavaScript وJSON وChart.js مقترحة في الدليل؛ لا اختيار نهائي.

**الخيارات:**

1. تطبيق متصفح بسيط بـ HTML/CSS/JavaScript وJSON، ومخططات عند الحاجة: تشغيل وعرض سريعان دون خادم؛ مشاركة الحالة بين المستخدمين أو حفظها خارج الجلسة ليست ضمن هذا الخيار تلقائيًا.
2. واجهة بإطار JavaScript خفيف: قد تفيد إذا كانت نور بدأت به بالفعل أو احتاجته مكونات الواجهة؛ يضيف أدوات بناء واعتماديات.
3. واجهة مع خادم صغير، مثل Python أو JavaScript: مفيد عند وجود حاجة مثبتة إلى تنفيذ مركزي أو حفظ نتائج؛ يضيف تشغيلًا وتكاملًا أكثر من حاجة القراءة الحالية.

**التوصية المقترحة:** الخيار الأول إذا لم توجد لدى نور قاعدة واجهة أنسب، بعد تجربة تشغيل قصيرة مشتركة من نور والريان. لا نضيف خادمًا أو قاعدة بيانات دون حاجة معتمدة. أدوات فحص البيانات الحالية مستقلة عن الاختيار ويمكن الاحتفاظ بها للاختبار حتى لو كان التطبيق JavaScript.

**الأثر:** يحدد القرار موضع منطق الحالة والتنبؤ والمحاكاة، طريقة التحميل، وكيفية مشاركة العقود مع الواجهة وتشغيل العرض على جهاز آخر. لا تنفيذ لمخزن حالة مشترك أو HTTP API ضمن Phase 1.

**المسؤولون عن الحسم:** نور + الريان وفق DEC-05؛ يُعرض الاختيار وآثاره على أحمد للمراجعة والاعتماد كمرشد ومعتمد قرارات المشروع، خاصة إذا غيّر خطة العرض أو نطاقه. تُبلّغ الجهات المتأثرة بالعقود.

## DEC-06 — مخطط JSON وعقود الربط

**الحالة الحالية:** الملف عينة اصطناعية متسقة ومتاح للفحص، لا مخططًا نهائيًا معتمدًا. مسودة العقد في `PROPOSED_FRONTEND_CONTRACT.md`.

**الخيارات:**

1. تثبيت أسماء وحقول v0.3 الحالية ووحداتها وقيمها كما هي، وتوثيق عقد القراءة والتحديث دون تغيير ملف المصدر.
2. اعتماد مخطط موحد جديد للحالات والقيم الفارغة أو إضافة حقول تشغيلية: يتطلب طلب تغيير، خطة ترحيل وعينة جديدة منفصلة واختبارات توافق.
3. اعتماد JSON Schema آلي إلى جانب القاموس والعقد: مفيد لاحقًا لتبادل البيانات، لكنه لا يحسم وحده معنى الحقول أو قواعد العلاقات والتحديث.

**التوصية المقترحة:** تثبيت عينة v0.3 الحالية أولًا بعقد صريح مع الإبقاء على اختلافات الأحرف والقيم `""` وموقع `Ambulance`. توثيق شروط الحقول وعلاقاتها قبل أي توحيد. يمكن إضافة مخطط آلي بعد اعتماد هذه الدلالات إذا خدم التكامل، دون ترحيل صامت للبيانات.

**الأثر:** تتوقف عليه حقول التحديث المسموحة وانتقالات الحالة، سلوك المعرف المفقود، غلاف الأخطاء، وحدات ETA، إصدار الحالة وانتشار أحداثها. لا ننشئ الآن مخططًا رسميًا أو حقول حالة/توصية/قرار جديدة داخل JSON.

**المسؤولون عن الحسم:** عبدالإله + نور + الريان وفق DEC-06. عمار وتاج يراجعان حقول الموارد والوحدات. وفق MPS §9، تعديلات عقود البيانات تحتاج موافقة أحمد وإبلاغ المتأثرين.

## مسائل يجب أن تحسم مع هذه القرارات

| المسألة | ما نعرفه الآن | الاعتماد المطلوب وأثره |
|---|---|---|
| أثر ETA في الطلب المتوقع | `predicted_incoming` لقطة ثابتة، وتغيير ETA وحده لا يغيرها | الريان مع عبدالإله ومراجعة أحمد: تحديد الأفق/نافذة الوصول وقاعدة التحديث؛ لا اختلاق زيادة أو انخفاض |
| السعة الفعالة | WARD-01 يتضمن 40 سريرًا، واحد منها `out_of_service` | تاج + عبدالإله + الريان وموافقة أحمد على القاعدة: هل يظل المقام 40 أم تصبح السعة الفعالة 39؟ لا تغيير الآن |
| إشغال الخلفية | إشغال ED-01 وRAD-CT يشمل مرضى غير مفصلين ضمن الخمسين | توثيق القاعدة مع عبدالإله؛ لا استبدال `occupied` بعدد `patients` |
| وحدات السعة | سعة ED/ICU/WARD أسرّة؛ RAD-CT وLAB-01 سعة استقبال مرضى دون أسرّة | تثبيت المعنى في DEC-06؛ لا جمع سعات الأقسام على أنها عدد أسرّة المستشفى |
| أوقات الخدمة والتدخلات | غير كافية لاشتقاق انتظار أو أثر موارد موثوق | الريان مع عبدالإله وعمار وتاج، واعتماد أحمد ضمن DEC-04؛ تبقى افتراضات اصطناعية معلنة |
| قواعد التوصية والقبول | المطلوب شرح وقرار قبول/رفض؛ ليس تنفيذًا طبيًا | اعتماد مقاييس المقارنة وحدود التوصية وسياسة النتائج القديمة. تطبيق تدخل العرض بعد قبول مسجل فقط |
| بنك الدم DEC-03 | غير ممثل في العينة الحالية وقرار تمثيله/تأجيله معلق في MPS | أحمد + عبدالإله؛ لا نضيفه ولا نعلن تأجيله بقرار ذاتي |

هذه المسائل تحجب الوظائف الديناميكية ذات الصلة، ولا تمنع تحميل العينة الحالية وفحصها للقراءة فقط. لا توجد موافقة ضمنية بسبب نجاح المدقق. طلب الاعتماد للفريق: اختيار DEC-04، ونتيجة تجربة نور والريان لـ DEC-05، واعتماد القاموس والعقد في DEC-06؛ ثم توثيق أصحاب الموافقة وتاريخها قبل بدء Phase 2.
